# w104 MVP — Design

**Date:** 2026-07-25
**Status:** Approved, ready for implementation planning

## Overview

w104 is a Jackbox-style couch party game. Players join from their phones; one
device acts as a shared TV screen. Everyone races to list as many items in a
category as they can before a timer runs out. Scoring is Boggle rules — an
entry scores only if no other player wrote it.

The MVP is one game mode: a single 30-second round, category "Women", scored
and displayed. Everything else in the product docs (category voting, teams,
brackets, contesting, score history) is explicitly out of scope and is designed
around rather than built.

## Starting point

The repo is a scaffold, not a partial implementation:

- `party/server.ts` — 51 lines: connection count + a "wave" broadcast.
- `src/main.ts` — the matching demo client, vanilla TS, `innerHTML`, no router.
- No database, no tests, no framework.
- CI deploys one Worker on push to `main`; Vercel deploys the web app.

Two claims in the product brief do not hold and shaped the decisions below:
there is no substantial backend to reference, and **a JSON file on the server
is not possible** — Cloudflare Workers have no filesystem. Durable Object
SQLite storage replaces it, and is already provisioned in `wrangler.jsonc`.

## Decisions

| Area | Decision | Rationale |
|---|---|---|
| Postgame | Static scoring page | Animated read-through and contesting deferred to v2 |
| Client | React on existing Vite | Six screens × two roles; hand-rolled DOM updates are where bugs live |
| Keyboard | Native, behind one component boundary | Autocorrect and swipe-typing matter in a 30s typing game; custom keyboard swaps in for boss-battle mode later |
| Host | Lobby creator is the host display, non-playing | Simplest rule; accepted cost is a 3-device minimum |
| Matching | Normalize + length-scaled edit distance | Closes the misspelling loophole without merging Anne/Anna |
| Environments | Two Worker environments (staging + prod) | PR previews must never touch live rooms |

## Architecture

Unchanged in shape from the scaffold: two deployables, both free tier.

```
Player phones ─┐
               ├─► Cloudflare Worker (PartyServer)   — one Durable Object per room
Host / TV ─────┘         │
       │  loads UI from  └─► DO SQLite: authoritative room state
       └─► Vercel (React SPA)
```

### Rooms and codes

`routePartykitRequest` maps `/parties/w104/:room` to a Durable Object keyed by
that string, so **the room code is the DO name** — no lookup table, no registry
service.

Codes are drawn from a bundled list of ~1000 short, unambiguous words.
Pronounceable beats random letters when the code is shouted across a room.

Collisions are resolved by the room itself, not a central allocator: the client
picks a candidate and connects with `intent: "create"`. If that DO already holds
state, it refuses and the client rolls a new code. A DO `alarm()` clears room
state after ~1 hour idle, recycling codes and releasing storage.

### State ownership

The Durable Object is the single source of truth. Clients hold a read-only
replica, replaced wholesale on each push. Every client action is a *request*;
the server decides what happened and re-broadcasts. Clients never mutate shared
state.

Three distinct types, because word lists must not leak mid-round:

```ts
// Server-only. The DO's complete picture. Never leaves the Worker as-is.
type Room = {
  code: string;
  hostId: string | null;
  players: Player[];
  phase: Phase;
  category: string;
  durationSec: number;
  lastActivityAt: number;              // last event time; drives the idle reap
  entries: Record<PlayerId, Entry[]>;  // everyone's words — server-side only
  kicked: PlayerId[];                  // players the host has banned — server-side only
};

// Broadcast to every connection on change. Safe for all eyes.
type RoomState = Omit<Room, "entries" | "lastActivityAt" | "kicked"> & { serverTime: number };

// Sent down one socket only, on reconnect.
type YourEntries = { entries: Entry[] };

type Player = {
  id: PlayerId;        // client-generated UUID, persisted in localStorage
  name: string;
  emoji: string;
  ready: boolean;
  connected: boolean;
};

type Phase =
  | { name: "lobby" }
  | { name: "countdown"; endsAt: number }
  | { name: "playing";   endsAt: number }
  | { name: "timesup";   endsAt: number }   // +3s, server-driven like the others
  | { name: "scoring";   results: Results };

type Entry = {
  text: string;        // as typed, preserved for display
  at: number;          // server receipt timestamp, ms
};
```

`entries` is a `Record`, not a `Map`: Durable Object storage serializes to
JSON, and a `Map` does not survive that round trip — a `Record` has the same
shape and access pattern without the loss. `toRoomState` is the privacy
boundary; it strips exactly `entries`, `lastActivityAt` and `kicked`, and
broadcasts every other field unchanged.

`RoomState` deliberately carries **no per-player entry counts**. Players must
not see how many words their competitors have, and shipping data no screen
renders is speculative traffic. The server holds counts in memory; adding a TV
ticker later is one field on one message.

### Traffic during a round

Once `playing` begins, `RoomState` is static — phase, roster, category, none of
which change for 30 seconds unless someone disconnects. Traffic is therefore
almost entirely one-way, player to server:

```
player A ──submitEntry{text, seq}──► server     // appends to entries[A]
         ◄──entryAck{seq, accepted}──┘          // A's socket only, ~30 bytes
```

The client renders each word optimistically on submit — a 30-second game cannot
wait on a round trip — then reconciles against the ack. The ack exists to carry
**rejections** (blank, over-length, already written); without it the player has
no way to learn an entry did not take. The full `YourEntries` list is sent only
on reconnect, to rebuild a phone that dropped mid-round.

Entries are sent per-submission rather than batched at the end because:

1. A phone that dies at second 28 loses nothing.
2. Server timestamps enable a future "first submission wins" scoring variant.
3. The v2 live cross-out feature requires the server to hold all words in real
   time; this design provides it at no extra cost.

### Timing

The server broadcasts `endsAt` as an absolute timestamp **once**; each client
renders its own countdown locally and corrects for clock skew using the
`serverTime` sent on connect. A DO alarm fires at `endsAt` to make the phase
transition authoritative.

Per-second tick broadcasts are explicitly rejected: they put every phone at the
mercy of party wifi, and a stuttering timer in a 30-second game is fatal to feel.

### Phase machine

Game logic is a pure function, `reduce(state, event) → state`. The Durable
Object is a thin shell that persists and broadcasts the result. The entire
game's rules then test in milliseconds with no Cloudflare runtime.

### Lobby rules

The host does **not** count as a player. A game requires **2 or more joined
players**, all marked ready; the countdown then starts automatically. The host's
"start game" button forces every player ready and triggers the same countdown.

Any player un-readying during the countdown cancels it and returns the room to
`lobby`. Minimum devices to play a game is therefore three: two phones and the
host screen.

## Protocol

There is no `hello` message. Identity and role arrive as query parameters on
the WebSocket URL (`?playerId=&role=&name=&emoji=&intent=`), so the server
knows who a connection belongs to — and whether it is the host — before it
accepts the connection at all. There is no unauthenticated window and no first
message to trust.

Client → server: `setProfile{name, emoji}`, `ready{ready}`, `startGame`,
`kick{targetId}`, `submitEntry{text, seq}`, `newGame`.

Server → client: `state{RoomState}`, `entryAck{seq, accepted, reason?}`,
`yourEntries{entries}`, `error{code, message}`.

`error.code` is one of `room-exists`, `no-such-room`, `game-in-progress`,
`not-host`, `kicked`.

`startGame`, `kick` and `newGame` are host-only and rejected from other
connections.

A kick is durable, not a one-off disconnect: the target's id is added to the
room's `kicked` list for the room's entire lifetime — `newGame` does not clear
it — their sockets receive `error{code: "kicked"}` and are closed, and any
later connection attempt with that id, including `partysocket`'s automatic
reconnect, is refused at the same query-parameter gate before it can seat them
again. The client treats `kicked` as a trip back to the landing screen, not
the generic error screen.

## Scoring

Runs once, server-side, on the `timesup → scoring` transition.

1. **Normalize** — Unicode-decompose, strip diacritics, strip punctuation,
   lowercase, collapse whitespace, trim. (`Beyoncé` → `beyonce`.)
2. **Dedupe within player** — silently, so writing "cat" twice never inflates a
   total.
3. **Cluster across players** — union-find over length-scaled
   Damerau-Levenshtein distance, measured against the shorter of the two
   strings:

   | Length | Allowed edits |
   |---|---|
   | < 5 | 0 (exact) |
   | 5–8 | 1 |
   | ≥ 9 | 2 |

4. Each cluster's display label is its most common spelling; ties break by
   earliest submission.

Eight players at 40 words each is ~51k comparisons — microseconds. No
optimization needed.

A cluster containing more than one player marks every member non-unique.

```ts
type Results = {
  players: {
    id: PlayerId; name: string; emoji: string;
    total: number;    // distinct words written
    unique: number;   // words no other player had
    entries: { text: string; unique: boolean; alsoBy: string[] }[];  // alsoBy = emoji
  }[];
};
```

Full `Results` ships to every client at once — the information is public by
then, and it feeds both the host table and each player's crossed-out list.

## Screens

Landing offers **Create** (become the TV, non-playing) or **Join** (code → name
+ emoji). Both roles then walk the same five phases, rendered differently.

| Phase | Player view | Host view |
|---|---|---|
| lobby | Roster, ready toggle | Room code large, roster + ready status, start, kick |
| countdown | 5…1 | 5…1 |
| playing | Category, numbered list, input | `NAME A: woman`, timer |
| timesup | "TIME'S UP" (3s) | "TIME'S UP" (3s) |
| scoring | Own total/unique, own list with duplicates struck and others' emoji | Score table, "New game" |

Because the client is a pure function of server phase, each screen is a
`switch` — there is no client-side transition logic to get wrong.

## Layout

Pure logic sits outside the Worker so it tests without one.

```
shared/   protocol.ts  state.ts  reduce.ts  scoring.ts  words.ts  categories.ts
party/    server.ts        # thin DO shell: persist, broadcast, alarms
src/      net/room.ts      # socket + useSyncExternalStore
          screens/{player,host}/*.tsx
```

`shared/` is referenced by both `tsconfig.json` and `tsconfig.worker.json`.

## Failure handling

| Situation | Behaviour |
|---|---|
| Identity | UUID in `localStorage` (see below); a reconnecting socket reclaims its seat and words |
| Host disconnects | Room survives, host marked disconnected, seat reclaimable |
| Player disconnects mid-round | Entries already server-side; player resumes on reconnect |
| New player joins mid-round | Refused; code stays valid for the next game |
| Player kicked | Banned for the room's lifetime, not cleared by `newGame`; sockets closed with `error{kicked}`; device returns to Landing; reconnect is refused |
| Blank / over-length / repeat entry | Rejected via `entryAck`, surfaced on the player's phone |
| Room idle ~1h | DO alarm clears state, code recycles |

Entry cap: 64 characters, 200 entries per player, as abuse limits.

### Identity storage

Player identity is a UUID under `w104:playerId` in `localStorage`. This is
chosen over `sessionStorage` deliberately: a phone that locks, backgrounds, or
has its tab closed mid-game must still reclaim its seat and its words, and
`sessionStorage` is discarded on tab close — the exact failure a party game has
to survive.

The cost is that `localStorage` is **shared across all tabs of one origin**, so
three tabs on `localhost:5173` all read the same UUID and the server treats tabs
2 and 3 as the same player reconnecting. They fight over one seat rather than
being three players. Separate phones are unaffected.

A dev-only override resolves this: a `?p=<n>` query parameter namespaces the key
to `w104:playerId:<n>`, so three ordinary tabs behave as three independent
players. Absent the parameter, behaviour is unchanged.

## Environments

Add a `staging` environment to `wrangler.jsonc`, yielding
`w104-staging.workers.dev` alongside production. CI deploys staging on pull
requests and production on merge to `main`. Vercel previews point at staging via
a per-environment `VITE_PARTYKIT_HOST`. Durable Objects are fully isolated
between environments, so a preview link can never collide with a live game.

Local development on one machine is unchanged: `npm run dev:party` +
`npm run dev`, no credentials required. Use `?p=1`, `?p=2`, `?p=3` across tabs
to simulate distinct players.

### Testing across real devices on the same wifi

The preferred way to test, since the game is played on phones and each device
gets its own `localStorage`. Three things must change, because nothing currently
binds beyond loopback:

1. **Vite** listens on `localhost` only — set `server.host: true` in
   `vite.config.ts`.
2. **Wrangler** likewise — `wrangler dev --ip 0.0.0.0` (folded into the
   `dev:party` script).
3. **`VITE_PARTYKIT_HOST` must be the host machine's LAN IP**, e.g.
   `192.168.1.42:8787`, in `.env.local`. This is the step that fails silently:
   the current fallback is `127.0.0.1:8787`, which from a phone means *the phone
   itself*, so the page loads normally and the socket simply never connects.

Both servers must stay on plain **http**. A page served over https cannot open a
`ws://` socket, so `--local-protocol https` breaks the connection; with both
sides on http there is no mixed-content problem.

Minimum for a full game loop is three devices — two players plus the host
screen — or three tabs using the `?p=` override.

## Testing

Vitest. None of the high-value tests require the Cloudflare runtime.

- **`scoring.ts`** — accent folding, the 5/9-character thresholds, the Anne/Anna
  non-merge, cross-player clustering, within-player dedupe, label selection.
- **`reduce.ts`** — readying early, un-readying during countdown, host leaving,
  kick, join-mid-round refusal, phase transitions.

The DO shell itself stays thin enough to need only smoke coverage.

## Out of scope for MVP

Animated read-through, contesting and vote/wager, score history and database,
category voting, time-limit voting, teams, alternate game modes, accounts,
drawn avatars, live cross-outs, pencil visuals.

Score history is the most likely next addition. It needs storage that outlives a
room; DO SQLite in a separate archive object or Cloudflare D1 both work on the
free tier. Not designed here.
